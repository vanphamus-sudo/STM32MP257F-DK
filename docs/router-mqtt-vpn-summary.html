Router → MQTT EC2
through the VPN

Keep the broker at 52.64.103.203:3003/TCP. Carry the router's connection inside OpenVPN to 3.24.63.90:1197/UDP, then forward it to the broker.

Proposed configuration · deployment not performed by this document
Two ports, two jobs. UDP 1197 transports the encrypted VPN. TCP 3003 is the MQTT broker connection carried inside it. The broker does not move to port 1197.

Replies travel back through the VPN EC2, which reverses the NAT translation and sends them through the tunnel to the router. The router's MQTT host, port, credentials and topics can remain as configured.

MQTT EC2
52.64.103.203		Keep the broker listening on TCP 3003. Allow TCP 3003 from the VPN EC2's public IP in the security group and host firewall. After testing and accounting for other clients, restrict broader public access to 3003. Preserve the separate TCP 3002 listener and access rules if other devices need them.

Make the router route persistent

The OpenVPN client configuration needs:

route 52.64.103.203 255.255.255.255 vpn_gateway

The router generates /etc/router-web/openvpn/client.conf; add the route to its persistent settings/configuration generator so later saves do not remove it. The current client uses route-nopull, so a route pushed only by the server is insufficient.

A /32 route covers every port on this one destination IP. Restricting routing to TCP 3003 alone requires policy routing. Ordinary Internet destinations continue to use the existing default route.

Verify the complete path

  1. Connect VPN: check router and server logs, tunnel addresses and successful tunnel traffic. Check UDP 1197 access if authentication never completes.
  2. Check routing: on the router, ip route get 52.64.103.203 should select tun-router.
  3. Reconnect MQTT: restart/reconnect the MQTT client so the test uses a new TCP connection. Observe TCP 3003 on the VPN server's tunnel and outbound interfaces.
  4. Confirm delivery: verify the broker sees the VPN EC2 public IP and receives a known test message. Where applicable, verify a subscribed reply reaches the router.
  5. Check persistence: reconnect the VPN and reboot the router; confirm MQTT resumes using the tunnel. Test the intended behaviour when the VPN is down.
Security boundary: OpenVPN protects the router-to-VPN-server leg. It does not automatically encrypt the onward connection to the broker. A port number alone does not prove TLS is enabled. For VPN-only MQTT, block direct router-to-broker TCP 3003 outside the tunnel; otherwise the normal route may be used after VPN failure.
